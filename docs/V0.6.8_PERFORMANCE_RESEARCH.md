# 大素材库预览性能研究

日期：2026-09-07。代码基线：`release/v0.6.8` / `7e8f020`。
本轮为诊断与技术方案，没有修改插件程序、重新安装插件、清理用户缓存或批量转码用户素材。

## 结论

需要本地预生成缓存，但不能把“一键生成所有代理”当成首要修复。
当前已经存在本地持久化缓存和虚拟列表，核心问题是任务生命周期、解码资源控制、
缓存读取依赖源文件 I/O，以及预览触发策略。先修这些，再增加可暂停/恢复的预缓存任务。

## 证据与根因

### 1. 滚动后仍被旧任务占位，已完成图片可能被丢弃

`extension/js/main.js:1478` 每次可见行变化递增全局 renderGeneration 并清空待处理队列，
但没有取消已执行的两个 UI 预览任务。`1696` 的 activePreviewJobs 仅在 Promise 结束时释放。
`1722` 又拒绝旧 generation 的返回值，即使该卡片仍在屏幕里。

提取实际函数做 mock 复现：旧任务两个占位；视窗 generation 更新；新可见卡片仍在排队；
旧 poster 完成后，因为 generation 不同，安装到卡片上的图片数为 0。
这证明逻辑问题，不是用户真实视频的耗时测量。

修复方向：媒体任务与卡片订阅生命周期分离；按资产 ID / 文件版本管理结果，保留仍可见
卡片的有效订阅。移除不再需要的任务或降低优先级，但不要每滚动一像素就全部重启。
缓存命中读取走独立快速通道，不被正在生成的旧图阻塞。

### 2. 雪碧图把同一个源文件同时打开 12 次

`extension/js/media-tools.js:1399` 循环产生 12 组 `-ss ... -i 同一文件`，用 xstack 拼图。
每一路都有独立输入/解码状态，解码器和复杂滤镜未限制线程数。
现有 MAX_FFMPEG_CONCURRENCY=2 是每个服务实例的进程数上限，不是解码器、CPU 或内存上限。
在 Pr 与 AE 同时打开时，各面板也没有跨进程的资源总预算。

软件代理分支 `media-tools.js:1048`、`:1150` 使用 `-threads 0`，允许自动线程配置。
即便并发只有一两个 FFmpeg，也可能占用许多核心和大量帧缓存。

### 3. 鼠标路过就产生额外工作，离开不取消

`main.js:1775` 的 mouseover 立即调用 spriteFor，没有悬停停留阈值。
`1819` 的 mouseout 只隐藏视觉状态，不取消或降级生成任务。它绕过 UI 的两任务海报队列，
不过仍受媒体模块底层队列限制。积累后，海报与雪碧图争用同一后台执行槽。
另一个 mock 确认鼠标离开后完成回调还能重新设置 is-scrubbing。

文件夹拼盘 `main.js:1652` 每个文件夹最多直接请求 4 个预览，也没有统一使用海报观察器队列。

### 4. 滚动海报失败可能升级成完整视频转码

`media-tools.js:1261` 的海报流程先查元数据，再尝试多个点；抽帧失败后，`:1295` 回退到
previewProxyFor(..., "720")，可能为一个卡片转码整个文件。黑场重试是必要保护，但失败
升级成高成本完整代理不应在被动滚动时自动发生。

选中播放 `main.js:1957` 总从原始文件启动；代理仅在首帧/播放失败后介入。可解码但很吃
资源的高规格视频会继续原画播放，没有按持续掉帧/负载自动选择代理。

### 5. 本地缓存已有，但不是真正的离线优先读取

缓存目录：`~/Library/Caches/com.fnnas.fnosbridge.mvp`。
当前只读统计约 741 MiB：1,943 海报文件约 287 MiB，601 雪碧图约 35 MiB，1,746 元数据
约 2 MiB，10 个视频代理约 217 MiB，另有音频/波形等。历史缓存不等于当前全部资产命中率。

`media-tools.js:516` 的源 stat 缓存仅 1.5 秒；海报和雪碧图读取本地缓存前都先等源文件 stat。
雪碧图还先等 metadataFor 再检查成图。SMB 响应慢或离线时，本地图已经存在也不能立即显示。
缓存键 `:1195` 包含 ctime/inode/dev，SMB 重挂载或文件身份变化可能造成重算；是否实际发生
必须通过重挂载前后的签名记录验证，不能只凭源码下结论。

`indexCache` 每次服务启动读取所有缓存文件信息；每次生成前的 pruneCacheInternal 会排序
并遍历当前缓存记录，未超预算时也做。这是规模扩大后的次级开销，而非截图卡顿的唯一解释。
海报、雪碧图和完整代理共用 12 GiB 配额，预生成大量代理可能挤掉低成本但高使用频率的海报。

### 6. 虚拟列表已经存在，不应重复“加虚拟列表”解决一切

`main.js:1442` 超过 160 项启用窗口化，`virtual-grid.js` 使用二分查询可见行；现有测试可访问
10,000 项且 DOM 有界。每次滚动仍有全数组分组与当前网格 detach/reappend，可继续优化，
但不应把成千个视频的解码压力误判为成千个 DOM 节点渲染。

### 7. 当前安装环境有版本歧义

当前用户 CEP 目录有同一扩展 ID 的两份内容：标准目录 manifest 为 0.4.0；一个名为
`.backup.20260905-215106` 的目录实际上是指向当前 0.6.8 源码的链接，仍处于 Adobe 扫描树内。
这不是普通安全备份。不能只凭目录推断截图实际加载哪份，但验收前必须核对面板/宿主版本和
真实路径，随后通过安装器迁移并完整重启 Adobe，确保仅有一个有效实例。本轮未操作安装目录。

## 受控算法对照

仅使用临时生成的 720p H.264：6 秒、24 fps、GOP 72、本地磁盘，FFmpeg 8.0.3 ARM64。
每种方式串行测两轮，进程优先级 nice +10、单次 15 秒截止；没有清系统页缓存，没有读取用户视频。
输出均为 960×408、12 格拼图。`/usr/bin/time -l` 记录峰值 RSS 和 CPU 时间。

| 算法 | 两轮墙钟耗时 | 两轮峰值 RSS | 两轮 CPU 时间 |
|---|---|---|---|
| 当前 12 输入、自动线程 | 151 / 147 ms | 963.41 / 965.19 MiB | 0.78 / 0.78 s |
| 同 12 输入，每路解码 1 线程、滤镜 1 线程 | 95 / 89 ms | 204.02 / 169.20 MiB | 0.46 / 0.45 s |
| 单路解码 2 线程、fps 抽帧 + tile | 62 / 61 ms | 29.45 / 29.14 MiB | 0.11 / 0.10 s |

前两种输出 JPEG 的 SHA-256 一致。单路 tile 使用不同采样时刻，不是逐帧等价替换。
这些数字只说明当前算法可产生显著资源放大；不是 4K、HEVC、长视频或 SMB 上的性能倍率承诺。
不能把整段 fps/tile 直接用于所有长片：它可能需要顺序解码全片，反而大幅增加总读盘与耗时。

原始实验脚本/JSON 位于本机临时目录 `/tmp/lkfb-performance-study-NcJvey`，用于本轮诊断。
现有虚拟网格和面板生命周期 6 项测试通过；随后完整 `npm test` 192 项也通过，0 失败、0 跳过，
静态与版本检查通过。但现有测试不覆盖本次复现的滚动 generation 与 hover 离开问题，
“192 项通过”不能代替大素材库的性能验收。

## 建议架构

### 分层缓存

| 层级 | 默认生成策略 | 存储与用途 |
|---|---|---|
| 资产索引 / 元数据 | 目录扫描或更新时小批量更新 | 本地持久索引，区分稳定资产 ID、源版本、生成配置、离线状态 |
| 静态海报 | 可见优先，随后用户可选择整库预生成 | 小尺寸 JPEG/WebP，浏览列表不接触视频解码器 |
| 雪碧图 | 悬停停留约 300 ms 后按需生成，或用户勾选预生成 | 本地图片及实际采样时间清单，滑动只是换图位置 |
| 播放代理 | 选中/预览高成本素材时，或用户明确批量生成 | 单独预算的 540p/720p H.264 播放文件；原文件用于 Pr 导入/剪辑 |
| 原始素材 | 不默认复制 | 保持原始路径引用，不为浏览整库复制一遍所有源视频 |

停留时间与分辨率是待验证初始值，不是最终规格。预览代理与 Pr 项目代理是两个概念：
本功能优先只加速插件浏览；除非另做经过验收的 Attach Proxy 集成，不改 Pr 的代理附着状态。

### 调度与资源控制

- 缓存命中独立读，不排在 FFmpeg 生成任务后面。用已知资产索引先显示本地图，源信息在后台
  校验；离线时明确标记“缓存预览”，不要让用户误以为源文件仍可导入。
- 用户当前播放/主动截图最高优先级，可见海报其次，停留悬停其次，视窗预取及批量预缓存最低。
- 拖动时暂停启动新的重生成任务；停下后恢复可见任务。取消仍在排队且不再需要的任务；
  对已经运行的任务按成本/完成度取消或降级，保留仍被其他卡片或宿主订阅的任务。
- 海报、拼盘、雪碧图、元数据和代理进入同一个调度接口，任务以资产版本和产物类型去重。
- 先把后台重解码压到 1 个、每路解码与滤镜显式限线程；结合观测数据设置 CPU/内存/读盘预算，
  不把“2 个进程”当成“资源有界”。主动播放时应暂停或进一步降低批处理吞吐。
- Pr/AE 多面板先加跨进程任务锁、去重与原子发布，避免同文件同时生成和互相清缓存；随后可
  将媒体工作统一到共享后台服务。CEP 的 DOM 窗口化继续保留，不在这轮重写整个前端框架。
- 同一 SMB 根路径限制并行随机读取，并按目录/源文件聚合工作；底层支持时才评估硬件解码，
  不默认认为 VideoToolbox 总更快或零 CPU 成本。

### 抽帧策略

- 首先限制现有命令线程，移除 12 路重解码并行放大。
- 短片可用单路顺序抽帧后 tile；长片比较“少量关键帧近似抽样”与“串行少量 seek 抽帧后拼图”。
- 若已经有播放代理，优先从低分辨率代理取图。不要为了生成一张海报无提示地转完整原片。
- 同一处理批次尽量复用元数据和解码结果，按实际采样时间做悬停映射。
- 保留黑场检查，但限定尝试次数、每项总耗时和失败重试退避；错误状态可见，不能无限后台重算。

## 一键缓存的产品形态

建议称为“准备离线预览”，明确范围是选中项 / 当前插件文件夹 / 所选素材位置。

- 默认：元数据与静态海报；可选雪碧图；播放代理独立勾选，不默认全选。
- 显示待生成数、已缓存数、失败数、预计空间；可暂停、继续、取消，软件重开可续跑。
- 选择本机缓存目录与空间上限。默认本地 SSD；可选外接 SSD，不把缓存默认放回 SMB。
- 批次仅更新新增或已变更素材；已完成产物原子落盘，任务清单持久化，取消不损坏已用缓存。
- 普通淘汰采用各缓存层独立配额；明确“保留离线”的项不能被自动淘汰，不足时提示释放或扩容。
- 清理缓存只清插件自己的可再生成产物，绝不删除源素材或作为工程素材引用的截图。

空间示例：2,000 条视频、每条 2 分钟、代理视频码率 2 Mb/s，约需 60 GB（十进制，不含音频）。
因此“全部先转代理”既耗时又容易挤占现有 12 GiB 缓存预算。静态海报通常远小于代理，但需实测
不同素材的图像压缩大小后再做整体空间预估，不能承诺固定每文件大小。

## 实施顺序与发布门槛

1. 第一阶段：排除重复安装；修正可见卡片完成回调与旧任务占位；缓存命中快路径；悬停停留
   与取消；限制解码线程；被动海报禁止自动转整片代理。先让现有浏览行为不拖垮电脑。
2. 第二阶段：低内存雪碧图策略、持久资产/缓存索引、后台源版本校验、跨宿主去重与资源预算。
3. 第三阶段：“准备离线预览”管理界面、暂停续跑、分层配额、离线保留及播放代理选项。

建议验收目标（尚未达成的目标，需真实 CEP 环境测量）：

- 1,000 / 3,000 / 10,000 项，缓存冷/热两种状态；本地 SSD 与 SMB、H.264/HEVC/ProRes、
  1080p/4K、短片/长片、不同帧率与码率，单开 Pr 与 Pr+AE 同开均覆盖。
- 热缓存停止滚动后首屏海报 P95 目标 <200 ms，且不因显示图片启动解码、不阻塞等待 SMB。
- 连续往返滚动不残留永久占位图；不再需要的排队任务能及时撤销，当前可见任务无饥饿。
- UI P95 帧耗时目标 <33 ms，无可感知长卡顿；同时记录主线程 long task、图片解码时间。
- 记录全部插件工作进程峰值 RSS、CPU、源盘读取速率、并行解码数、等待队列长度和缓存命中率，
  预算按 Mac 型号校准。目标是给 Adobe 编辑保留资源，而不是离线预生成速度最大化。
- 打开/关闭面板和重复滚动 30 分钟后资源回落，无持续上涨；中止、断网、低磁盘空间可恢复。
- 预缓存暂停后不再启动下一项；重启可续跑；清缓存不触碰源素材或工程引用。

当前截图不足以把 AE 的全部内存归因于插件。现场采样未捕获运行中的 FFmpeg；系统有大量
已使用 swap，但 swap 数值本身不证明此刻正在高频换页。下一轮需录制同一滚动操作的 CPU、
CEP/FFmpeg RSS、内存压力与磁盘读取时间线，才能完成实际环境的因果归因。

## 参考

- [FFmpeg 输入模型与 seek](https://ffmpeg.org/ffmpeg.html)：每个 `-i` 创建独立输入；精确 seek 可能从更早关键点解码后丢弃帧。
- [FFmpeg 复杂滤镜线程](https://ffmpeg.org/ffmpeg.html#Advanced-options)：`filter_complex_threads` 默认按可用 CPU 设置。
- [FFmpeg tile](https://ffmpeg.org/ffmpeg-filters.html#tile)：可把连续选出的帧拼接成一张图，不要求 12 路输入。
